# 项目架构说明

这个项目是一个小车控制系统，当前的设计原则很明确：

- 板子上的 Python 程序负责最终控制
- 电脑端只负责发输入状态，不直接碰电机
- C++ 桥接层和 `libu2canfd.a` 保留，用来和硬件通信
- 控制逻辑、输入层、校准层、遥测层彼此分离，方便重构和排错

## 1. 总体分层

```text
手柄 / 远程输入
    -> 输入层
    -> 控制器 CarController
    -> 模式层 mode0 / mode1 / mode2
    -> 安全层
    -> 电机客户端
    -> C++ 桥接层
    -> libu2canfd.a / CANFD / 电机
```

再往上还有两类辅助层：

```text
控制台遥测 / JSONL 日志 / 校准报告
只读 HTTP API / 前端仪表盘
部署脚本 / 环境检查脚本 / 测试脚本
```

## 2. 目录职责

### `app/`

程序入口。

- `app/main.py` 负责解析参数、装配对象、启动主循环

### `car_control/`

核心控制逻辑都在这里。

- `controller.py`：总调度器，串起输入、模式、安全、电机输出
- `gamepad_input.py`：本地手柄输入
- `network_input.py`：远程 UDP 输入、hybrid 接管
- `input_filter.py`：死区、曲线、平滑
- `mapping.py`：摇杆到速度/角度的映射
- `kinematics.py`：运动学计算
- `mode0_rotation.py`：原地旋转/兼容模式
- `mode1_steering.py`：正常遥控车转向模式
- `mode2_safe_debug.py`：低速安全调试模式
- `safety.py`：急停、回中、驱动轮停止
- `motor_client.py`：电机客户端封装，支持 mock 和真机桥接
- `telemetry.py`：控制台面板、JSONL 遥测
- `state.py`：模式状态、方向锁状态等运行态
- `types.py`：输入数据结构

### `configs/`

运行时配置。

- `hardware.json`：硬件 ID、轮子参数、桥接库路径
- `control.json`：控制参数、模式参数、限速参数
- `input.json`：手柄映射
- `network.json`：UDP 远程输入配置
- `control_profiles.json`：不同调参挡位

### `scripts/`

部署、校准、验证脚本。

- `setup_board.sh`：板子环境检查
- `build_bridge.sh`：编译 C++ 桥接层
- `run_mock.sh`：纯 mock 验证
- `run_hardware.sh`：板子真机运行
- `calibrate_hardware.py`：硬件校准向导
- `deploy.sh` / `deploy.ps1`：部署脚本

### `docs/`

说明文档。

- `USAGE.md`：使用流程
- `REMOTE_CONTROL.md`：远程控制说明
- `TUNING.md`：调参说明
- `DEPLOY.md`：部署说明
- `BACKEND_INTERFACE.md`：后端接口说明
- `FRONTEND_API.md`：前端只读接口说明

### `tests/`

单元测试与行为测试。

## 3. 运行数据流

### 3.1 本地手柄模式

```text
本地手柄 -> PygameGamepadInput -> CarController -> 模式层 -> 电机客户端 -> 硬件
```

### 3.2 远程模式

```text
电脑端手柄 -> UDP 发送器 -> 板子 UdpRemoteInput -> CarController -> 硬件
```

### 3.3 混合模式

```text
本地手柄 + 远程输入 -> HybridInputSource
    -> 本地急停优先
    -> 远程新鲜时接管
    -> 远程超时自动回本地
```

## 4. 控制链路

主循环的核心顺序是：

1. 读取输入
2. 输入过滤和平滑
3. 判断是否切模式
4. 进入对应模式逻辑
5. 经过安全层修正
6. 下发给电机客户端
7. 输出遥测

对应入口在 [app/main.py](../app/main.py) 和 [car_control/controller.py](../car_control/controller.py)。

## 5. 三种控制模式

### mode0

保留原项目兼容逻辑，偏原地旋转和特殊动作。

特点：

- 可以让驱动轮和转向轮进入固定策略
- 适合兼容老控制方式

### mode1

正常遥控车模式，偏 Ackermann 转向。

特点：

- 以左摇杆控制前进/后退
- 以横向输入控制转向
- 会做转向和速度联动
- 是现在最接近“遥控车”的主模式

### mode2

低速安全调试模式。

特点：

- 降低速度
- 方便现场验证方向、转向、零点和电机回显

## 6. 硬件层

硬件层没有被重写。

当前保留的是：

- C++ 桥接层
- `libu2canfd.a`
- CANFD / 电机通讯逻辑

Python 不直接替代这层，而是通过 `motor_client.py` 调用它。

这样做的原因很简单：

1. 避免重写底层通讯风险
2. 保留原本已经能跑的硬件能力
3. 让控制逻辑和硬件解耦，后续更容易重构

## 8. 遥测和排障能力

当前遥测已经能直接看到：

- 当前模式
- 输入源
- 链路状态
- 远程序号
- 远程时延
- 远程是否过期
- 急停状态
- 左右摇杆输入
- 驱动轮目标/实测/误差
- 转向轮目标/实测/误差

这意味着现场排障时，基本能快速判断问题属于：

- 输入问题
- 网络问题
- 电机回显问题
- 控制逻辑问题

## 10. 当前推荐使用方式

现场最稳的顺序是：

1. 先跑 `--mock`
2. 再跑 `mode2`
3. 再跑本地手柄真机
4. 再上远程 / hybrid
5. 最后再做参数调优

如果你要重构，这个顺序不要乱。
